# data_quality_metrics

dbt-проект с двумя warehouse: **ClickHouse** (`dq`) — шум алертов и дрейф категориальных распределений (PSI); **Postgres** (`lineage`) — здоровье графа lineage.

Профиль лежит в `profiles.yml` (gitignore) или копируется из `profiles.yml.example`. Запуск из корня проекта:

```bash
# ClickHouse: алерты, метрики шума, PSI
dbt build --profiles-dir . --target dev_clickhouse

# Postgres: здоровье графа
dbt build --profiles-dir . --target dev_postgres
```

Модели в `models/clickhouse/` включаются только на ClickHouse, в `models/postgres/` — только на Postgres.

## Часть 1. Диагностика шума

Продакт: дежурные игнорируют алёрты из‑за объёма и низкой точности. Ниже — перевод жалобы в числа.

### 1.1 Двадцать самых шумных проверок — `alerts_checks_twenty`

Шум — не только частота. `noise_score` складывает:

- интенсивность: алерты в день (`alert_count / active_days`);
- длительность: доля активных дней за 30 суток;
- тяжесть: `critical × 3 + warning × 1`;
- повторяемость в одном срезе: `alert_count / distinct_windows`.

Топ-20 по `noise_score` за 30 дней, срез: channel / event_channel / subchannel / event_type / event_subtype / check_name.

### 1.2 Доля ложных срабатываний — `alerts_lay`

По `alert_labels` за 30 дней:  
`(false_positive + known_issue) / (true_positive + false_positive + known_issue)`.

`known_issue` в числителе FP только если таксономия явно так определяет; иначе это отдельный статус.

Оценка смещена:

- **selection bias** — размечают не все алерты;
- **self-selection** — чаще уверенные случаи, спорные остаются без метки;
- **temporal bias** — свежие алерты размечают чаще старых.

Чтобы цифра стала честной: случайная (лучше стратифицированная) выборка, SLA на разметку, отдельный статус «нет разметки», взвешивание по вероятности отбора.

Join сейчас по `window_start + channel` — зерно грубое; при нескольких алертах в окне счётчики раздуваются.

### 1.3 Незрелый профиль — `alerts_lay_no`

Гипотеза: часть алертов из бакетов `hour_of_week` с малым числом наблюдений.

Гейт: **не выпускать алерт**, если `n_samples < 30` **или** `total_count < 1000`.

- `n_samples ≥ 30` — стартовый практический порог, его нужно подтвердить историей FP.
- `total_count ≥ 1000` — ограничивает дисперсию долей; калибруется бэктестом.

### 1.4 Ещё три причины FP

| Причина | Модель |
|---|---|
| Сезонность внутри дня | `seasonality_intraday` |
| Выбросы в знаменателе (`total_count < 50`) | `denominator_outliers` |
| Задержка окна (`dateDiff > 15` мин) | `latency_delay` |

## Часть 2. Метрика дрейфа распределения

Проверки ловят сдвиг уровня, но не смену формы (USD 92% → 85%, EUR симметрично вырос). Нужен дрейф категориального распределения.

### 2.1 Почему PSI — `psi`

- шкала: `< 0.10` норма, `0.10–0.25` умеренный, `> 0.25` сильный — понятна риск-валидатору без p-value;
- раскладывается по категориям (вклад USD vs EUR);
- симметричен: `PSI(P, Q) = PSI(Q, P)`.

Наивная формула без хвоста и сглаживания — модель `psi`. Боевой расчёт — `psi_other` на базе `psi_shares`.

### 2.2 `category_counts` Map(String, Int64)

Схема не меняется: джоб пишет map, профиль складывает `sumMap()`, расчёт разворачивает `ARRAY JOIN mapKeys/mapValues`.

Минусы: высокая кардинальность, каждый запрос разворачивает map, нет места под атрибуты и историю категории. Отдельная таблица нужна, когда фильтрация по категории частая, нужен SLA или версионирование.

### 2.3 Полный расчёт — `psi_shares` → `psi_other`

- **Новые / исчезнувшие категории:** full outer join, отсутствующей стороне `count = 0`.
- **Сглаживание:** Laplace `α = 0.5`, доли `(count + α) / (total + α × 4)`, чтобы `ln` не давал inf/NaN.
- **Хвост:** top-3 категории профиля остаются именованными, остальное на обеих сторонах в `__other__`.
- **Гейты:** `total_count` окна и профиля ≥ 100, `n_samples` профиля ≥ 30.

### 2.4 Пороги severity — `psi_severity`

| PSI | severity |
|---|---|
| `< 0.10` | info |
| `0.10–0.25` | warning |
| `≥ 0.25` | critical |

Это стартовые ориентиры, не стандарт. До выката: 8–12 недель `metrics` + `baseline_seasonal` + размеченные алерты, разметить инциденты vs норму, посчитать Precision/Recall, крутить порог. Для запуска — согласованные Precision/Recall (ориентир > 0.7 / > 0.8), holdout и приемлемое число алертов на смену.

### 2.5 Payload для дежурного — `psi_details`

Колонка `details` — JSON за ~15 секунд: общий PSI, severity, top-3 вклада категорий (baseline/actual share, direction, psi_contribution), new/disappeared, объёмы, версия профиля, `contributions_sum_check`.

### 2.6 Что отвергнуть

**Хи-квадрат.** На миллионах событий χ² растёт с N: статистически значимо то, что бизнесу безразлично. Нужна метрика размера эффекта с откалиброванными порогами, не p-value.

## Часть 3. Здоровье графа lineage

### 3.1 Метрики на дашборд

| Метрика | Модель | Ухудшение → действие |
|---|---|---|
| Доля dataset без рёбер | `dataset_orphan_pct` | дыра в сборе → проверить коллектор и парсинг |
| Table-lineage без column-lineage | `dataset_missing_column_pct` | нет колоночного покрытия → донастроить парсер SQL |
| Узлы/рёбра по сборщикам | `collector_distribution` | перекос или обнуление source → инцидент сборщика |
| Конфликты владения ребра | `edge_ownership_conflicts` | два source на одно ребро → разобрать приоритет |
| Активность сборщиков | `collector_activity` | `lost_collection` → алерт «потеря сбора» |
| Устаревшие рёбра при живом сборщике | `stale_edges` | пайплайн, скорее всего, выключен → уведомление владельцу |
| Доля рёбер marked_for_deletion | `marked_for_deletion_pct` | рост очереди на удаление → чистка графа |

### 3.2 SQL

Реализовано моделями из таблицы выше.

### 3.3 Знаменатель «полноты покрытия»

Точного числа «сколько таблиц должно быть в графе» нет. Три оценки, все врут:

1. **Каталог СУБД** (`information_schema` / `system.tables`) — завышает: служебные, временные, стейджинговые таблицы, которые не должны быть в lineage.
2. **Логи запросов / audit** — занижает: редкие и batch-only таблицы могут не попасть в окно логов; завышает ad-hoc.
3. **Inventory / CMDB / data catalog** — отстаёт от реальности и зависит от дисциплины заполнения; обычно занижает теневые витрины.

Имеет смысл показывать три знаменателя рядом, а не один «процент покрытия».

### 3.4 Устаревание vs потеря сбора

Двухуровневый сигнал:

1. `collector_activity` — если source не подтвердил ни одного ребра за 2 дня → **потеря сбора** (пайплайн, скорее всего, работает, метаданные не приходят).
2. `stale_edges` — `last_seen_at` старше 30 дней, но сборщик жив → **честное устаревание**, кандидат на удаление, уведомление владельцу пайплайна.
